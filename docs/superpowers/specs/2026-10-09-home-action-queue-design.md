# Очередь действий и сроков на главных экранах

9 октября 2026. Пользователь выбрал эту следующую итерацию в Ralph. Работа продолжается от плана найма и общего шага; переговоры до контактов остаются отдельной задачей.

## Выбранный подход

Одна серверная очередь по уже принятым приглашениям вместо чтения всех приглашений и отдельного запроса для каждого шага. Первый вариант проще на уровне API, но требует N запросов, усложняет отзыв прав и не доказывает полноту первой страницы приглашений. Отдельная read-only проекция использует существующие шаги, согласия и разрешения, без новой модели найма или миграции.

## API и доступ

GET `/api/v1/me/next-steps?limit=5&cursor=...` доступен обеим ролям. Кандидат читает только собственные обсуждения; компания — только свою очередь с подтверждённым email и действующим owner membership. Каждый элемент требует принятого приглашения и именно его исходного активного contact_grant_id, с совпадающей парой компании/кандидата. Выполненные шаги, приглашения без шага, непринятые приглашения, удалённые кандидаты и отозванные архивы не включаются. Архив по-прежнему читается кандидатом в самом диалоге.

Элемент NextStepQueueItem: invitation_id, invitation_version, company_name из снимка, candidate_display_name (nullable), candidate_visibility (public/hidden), is_my_action, step (существующий HiringNextStep). Имя кандидата доступно только по существующему публичному предикату: visibility public, email подтверждён, пользователь не удалён, текущие processing/publication consents действуют. Применяется существующий PublicTextRedactor. При скрытом имени компания видит нейтральную подпись обсуждения с кратким ID приглашения. Контакты, приватные заметки, оценки и новые сведения об участнике не читаются и не выдаются.

NextStepQueuePage: items, next_cursor (nullable), limit. Limit от 1 до 100, default 5. Сервер получает limit+1; наличие следующего курсора означает неполную выдачу. Ошибка, загрузка и частичная выдача не называются нулём.

Порядок: шаги для текущей стороны первыми; затем due_at ASC NULLS LAST; updated_at ASC; invitation_id ASC. is_my_action определяется ответственным по плану: candidate для кандидата, company для компании. Курсор связан с viewer id/role и содержит точные ключи такого порядка. Для null deadline используется SQL infinity только внутри сортировки/seek, никогда в DTO. Некорректный, слишком длинный или чужой курсор возвращает 400. Очередь живая, а не фиксированный снимок: изменение порядка между страницами может требовать обновления; клиент объединяет по invitation_id и регулярное обновление начинает с первой страницы.

## Интерфейс

На обеих главных — блок «Действия и сроки» с action, стороной по плану, датой с часовым поясом и ссылкой `/messages/{invitation_id}`. Шаги для себя и ожидания различаются, но не объявляются согласованными обязательствами кандидата. Истёкший срок — «Срок по плану прошёл», без штрафа, изменения грейда или ранжирования. Неуказанная дата показывается явно. Выполненные и архивные записи не создают активных действий.

Кандидатская основная рекомендация сохраняет порядок: активная оценка → известные ожидающие приглашения → известный собственный общий шаг → прежние действия согласия/профиля/подтверждения/видимости. Общий шаг не запускает тест и не раскрывает контакты. Положительный счётчик приглашений остаётся нижней границей, пока список не исчерпан.

Загрузка, ошибка, отсутствие актуальных шагов и следующая страница — разные состояния. «Показать ещё» читает серверный cursor; ошибок страницы не скрывает. Перед refocus/visibility refresh старые элементы и данные очереди очищаются. При 401/403/404 также убираются. Каждые 30 секунд на видимой вкладке выполняется revalidation. Запоздалые ответы после смены пользователя, роли, страницы или ревокации не восстанавливают старые данные. Редактирование остаётся в существующем диалоге; дополнительных форм и новых зависимостей нет.

## Приёмка

1. Обе роли видят только актуальные незавершённые шаги по своей области доступа.
2. Отзыв исходного grant исключает запись, даже если другая версия/приглашение создали новое разрешение пары. Скрытие профиля убирает имя, сохраняя только доступный общий шаг.
3. Собственные действия первыми, даты по возрастанию, null последними, tie order устойчив. Пагинация проходит оба вида сроков и обе группы; чужой/malformed cursor и limit вне диапазона отвергаются.
4. Активная попытка и pending invitations сохраняют приоритет основного CTA; собственный общий шаг доступен до повторной оценки/дополнения профиля.
5. Refocus, logout/role change, initial/next-page errors и запоздалый response не возвращают приватные строки и не имитируют пустую очередь.
6. На desktop/mobile читаются действие, сторона, срок и переход; keyboard и reload проверены.
7. Замороженные assessment/matching и manifests сохраняют исходные SHA-256; исходные посторонние Git-изменения не перезаписываются.

## Доказательства и границы

Свежие HTTP/unit/build/runtime проверки, независимый architect и changed-files standard ai-slop-cleaner с повторной регрессией обязательны. Нет обещания мгновенного realtime-отзыва, измеренного ускорения найма, новой валидизации банка или выпуска внешнего стенда. Push прежнего коммита остаётся заблокирован до destination-specific разрешения; эта итерация не пытается его повторить.
